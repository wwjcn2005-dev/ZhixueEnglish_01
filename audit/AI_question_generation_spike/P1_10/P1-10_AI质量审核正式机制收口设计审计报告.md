# P1-10 · AI 质量审核正式机制收口设计审计报告

最终结论：**`P1-10_DESIGN_PASS`**

```text
AI 调用 = 0 · 正式 DB 写入 = 0 · 正式教材数据 = 0 修改
本阶段只读：question_library.db（?mode=ro）、learning.db、contentpack、
            P1-01～P1-09-G 全部产物、现有代码
唯一交付物 = 本报告
```

一句话结论：

> **机制可以收口，但不能靠"AI 证明答案唯一"。**
> 收口后的正确形态是：**教材证据决定"能出多少题、出什么题型"（0 题是正常结果）；
> 程序负责硬事实；AI 只提供英语与教育质量的中文意见；答案唯一性只做风险提示
> （填空永远宣告"无法证明"）；人工只回答一个问题——"这道题是否采用"，
> 而生命周期完全由现有硬门槛控制。**

本报告同时给出 3 项**必须落地否则收口无效**的机制件（§12），它们不是设计矛盾，而是设计的必要落地件。

## 3. 新核心原则（收口后的第一原则）

```text
有多少有效教材资源，就用多少；有就生成，没有就算。

不设固定题数。
不要求每个 Section 必须产生题。
不为了凑题数创造学习点。
不为了提高数量而放宽质量标准。
没有足够有效证据时，允许生成 0 题。
```

这条原则的**优先顺序高于**任何"题量均衡""题型覆盖率""每节至少 N 题"之类的指标；
本项目在任何文档、脚本或界面中都不得再引入上述指标作为生产目标。

### 3.1 这条原则为什么必须现在写死

```text
真实数据已经证明：资源少的场景会出现 0 题（P0 第三场景实测返回 0 题 + 理由）；
而现有正式数据把 0 题一律记成失败（§2.3 的 7 行）。
如果不先把原则与状态定义写死，"0 题=失败"的默认心智会让下游为了"避免失败"而补题，
这恰好是项目最禁止的行为。

## 4. 0 题与失败的正式定义

### 4.1 「有资源就生成，没有就 0 题」发生在哪一层

```text
发生位置：**Section 级 AI 生成之后、生成完整性检查之前** ——
即 "Section 证据组装 → AI 生成 0~N 题" 这一步的输出判定。

判定顺序（必须固定）：
  step 1  API/服务层是否成功？（HTTP、鉴权、超时）
  step 2  输出是否完整可解析？（finish_reason、JSON、结构合法）—— 由 generation_guard 负责
  step 3  解析后 questions 的数量：
            0 题 + 明确理由  → **SUCCESS_ZERO_QUESTIONS（正常结果）**
            ≥1 题            → 继续走完整性检查 → 程序硬校验 → 候选题
  任何一步失败            → **GENERATION_FAILED**（工程失败，不是内容判定）
```

### 4.2 两个结果集的正式定义

**A. 正常 0 题 —— `SUCCESS_ZERO_QUESTIONS`**

```text
判定条件（必须同时满足）：
  1. API 与 guard 层面成功（finish_reason=stop、content 非空、JSON 可解析、结构合法）
  2. questions = []，且响应中带有可记录的理由
     （证据不足 / 没有足够明确的学习点 / 资源不适合安全出题 / 只有重复内容 /
       材料不足以支撑答案 / 当前题型没有可靠证据）
  3. 有完整调用账目（模型、prompt_version、context_hash、usage、时间）

典型场景（任务书列举，全部允许）：
  有教材内容但没有足够明确的学习点
  当前资源不适合安全出题
  只有重复内容
  只有不足以支撑答案的材料
  当前题型没有可靠证据（例如只有音频引用、没有文字稿 —— P0 第三场景即此类）

这是正常结果，不是失败，更不是"质量好"。
```

**B. 生成失败 —— `GENERATION_FAILED`**

```text
API 失败 / 鉴权失败 / HTTP 错误
JSON 损坏或结构无法解析
finish_reason = length（截断）
输出明显违反生成协议（禁止字段、题型非法、缺少必需字段）

这是工程失败，必须按现有纪律立即停止（不解析、不补救、不重试、不入库）。
```

### 4.3 与现有实现的差距（必须明确写出）

```text
① 目前 generation_guard 只有 4 个状态：OK / TRUNCATED / EMPTY_CONTENT / API_ERROR
   → 第 3 步"0 题 vs 有题"完全没有状态，guard 返回 OK 之后没有任何地方区分这两者

② 但 generation_run 已有可与本设计直接对接的字段：
   status: OK / TRUNCATED / API_ERROR / **INSUFFICIENT_EVIDENCE**
   insufficient_evidence: 0/1，CHECK 要求 =1 时 status 必须是 INSUFFICIENT_EVIDENCE
   → "正常 0 题"**今天就有合法的落库位置**（status=INSUFFICIENT_EVIDENCE +
     insufficient_evidence=1 + note 写明具体理由），**不需要任何 schema 变更**

③ 实测：0 行使用过；7 行 q=0 全部被记成 TRUNCATED/API_ERROR
   → 机制件已在 schema 里，语义与写入路径从未接通。这是 §12 的 B1
```

### 4.4 一处必须澄清的语义边界

```text
"0 题"在**生成层**是正常结果；
但在**校验层**必须记录为"无题可验证"，绝不能记成 PASS。
（P0 第三场景已确立该口径：validator_executed = false、rows = []、
  pass = 0、fail = 0，并明确写下"0 题不得被解释为 PASS"。）
```

### 4.5 历史数据是否需要重标

```text
不需要。7 行 q=0 全部是真实的工程失败（6 行截断、1 行接口错误），
与新定义的"正常 0 题"不是同一类事件；本轮不修改任何历史记录。
```

## 5. 资源驱动的题型机制

> 题型是**资源决定的可选项**，不是 **Section 必须完成的配额**。

### 5.1 正式表述

```text
每个 Section 允许出现的题型组合完全由该 Section 的证据决定：
  有大量重点词、没有合适阅读信息 → vocab_choice 3 / fill 2 / reading_choice 0 / judge 0
  有完整阅读文本、没有重点词空位   → vocab_choice 0 / fill 0 / reading_choice 4 / judge 1
  只有 1 个高价值学习点            → 1 question
  没有可安全出题的证据             → 0 question
以上四种都是正常结果。
```

### 5.2 支撑证据（真实数据）

```text
Starter · GET_READY     fill 3 + reading_choice 1（无 vocab_choice、无 judge）
Unit 1 · UNDERSTANDING  fill 4 + vocab_choice 3（无阅读、无 judge）
Unit 2 · UNDERSTANDING  fill 2 + vocab_choice 2 + reading_choice 2（无 judge）
Unit 5 · UNDERSTANDING  vocab_choice 1 + reading_choice 1 + judge 2（**无 fill**）

→ 4 个 Section 的题型组合互不相同，且没有任何题型全覆盖。
  说明"资源驱动"在实践里已经发生，本轮只是把它写为正式原则。
```

### 5.3 与现有提示词的关系

```text
P1-05-v3 已写明"不设固定题数""有合适就多生成、没有就少生成、没有合适可以 0 题"，
且 P0 第三场景实测模型会真的返回 0 题且不凑数。
→ 本原则在**提示词层已存在**，缺的是**程序层与数据层的承认**（§4.3）。

## 6. AI 质量审核机制（正式定位）

### 6.1 定位

> **独立第二层英语质量检查 + 给人看的辅助意见。**
> 它不是自动批准器，不产生任何生命周期结论。

### 6.2 审核维度（保持 P1-09-A 的六维框架）

```text
1 english_correct     英语正确性
2 answer_unique       答案唯一性（定位见 §7，非证明）
3 naturalness         自然度
4 learning_value      学习价值
5 distractor_quality  干扰项质量（仅选择题）
6 grade_fit           年级适配
```

### 6.3 权限边界（实测支持）

```text
AI 可以：输出 PASS / CONCERN / FAIL；提出风险；给出中文说明
AI 不可以：直接 APPROVED；直接 ACTIVE；修改 lifecycle；替代人工最终确认
```

证据：P1-09-B / D / F 三轮真实调用中，AI 输出全部落在审计目录，未产生任何 `question_event`、
未改变任何状态；6 个触发器始终在位（P1-08-C 的 12 项拒绝测试全通过）。

### 6.4 输入契约（沿用 P1-09-C，已实测有效）

```text
必须给：题干 / 选项 / 给定答案 / 教材位置 / **证据块全文** / 作答标准 / 年级背景
禁止给：validator 结论、gate 结果、mechanical_rewrite 程序标志、lifecycle、
        生成 explanation、生成 prompt、已知问题标签、内部 ID

已实测的两个效果：
  · 给"证据块全文"而非摘录 → 消除 P1-09-B 的 evidence_concern 误报（P1-09-C 定位的根因）
  · 上下文确实不足时输出 CONTEXT_INSUFFICIENT，且不升级成 REJECT（P1-09-D 实测 2/2）
```

### 6.5 不稳定的维度必须如实标注

```text
learning_value：P1-09-B 实测检出率 1/2，是最弱维度 → 未验证充分前不得作为阻塞依据
distractor_quality：口径在"阅读题 vs 现实常识"两种标准下不稳（1/2）
answer_unique：见 §7
```

## 7. `answer_unique` 的最终定位

### 7.1 选择题：**风险检测 + 辅助审核信息**（不是唯一性证明）

```text
机制：候选集合天然完整（= 题目选项）→ AI 逐个候选判断
      （grammar_valid / semantic_valid / textbook_context_valid / reason_cn）
      → 程序按三字段重算并汇总

实测（P1-09-F，2 个真实 fixture）：
  · 发现真第二答案 2/2（旧协议为 0/2）→ 召回能力成立
  · 但 6 个非当前答案候选中 5 个被判为有效（83%）→ 精度低

→ 结论：`UNIQUE_RISK` 的正确含义是"**需要人工看一眼**"，
  绝对不是"这道题有问题"，也不是"不能采用"。
  它不构成 APPROVED / ACTIVE 的任何条件，也不构成拒绝理由。
```

### 7.2 填空题：**`answer_unique_status = NOT_PROVABLE`**

```text
依据：P1-09-E 已确认现有正式数据无法建立"既完整又可控"的填空候选池
      （能覆盖真实第二答案的池有 225–2,062 个词，且全教材正文 87% 的词没有词性；
        能用的池 1–117 个却漏掉两个真实第二答案）
      P1-09-G 进一步确认：确定性预筛 80% 误标、并漏掉 FIX-C1，判定 BLOCKED。

因此：
  fill 不使用逐候选证明机制
  fill 不得输出 UNIQUE_SUPPORTED
  fill 的唯一性状态恒为 answer_unique_status = NOT_PROVABLE，coverage = NONE
```

### 7.3 这一定位为什么**不应该阻塞整个题库系统**

```text
1. 唯一性只是 6 个维度中的 1 个；其余 5 个维度（英语正确、自然度、学习价值、
   干扰项、年级适配）与唯一性相互独立，已实测可用。
2. 本项目采用"教材锚定"作答标准：学生在课文在手的情况下练习。
   在教材语境下答案由课文决定，属于该题型的正常设计；
   唯一性风险针对的是"脱离课文单独使用"的场景，而不是"能不能用"。
3. 唯一性风险的处理方式是"提示 + 人工确认"，而不是"自动拦截"。

→ 如果其他质量维度良好，填空题与其他题仍可正常进入人工审核；
  中文审核摘要必须写明"填空答案唯一性无法由系统可靠证明"，
  由最终审核决定是否采用，**不得自动 ACTIVE**。
```

### 7.4 与现有 lifecycle 是否一致

**一致。** 逐条核对：

```text
· 生命周期链完全不变：PENDING_REVIEW → 人工 REVIEW_APPROVED → APPROVED →
  显式 ACTIVATED → ACTIVE（P1-08-C 已验证：未审核不能 ACTIVE、APPROVED 不会自动 ACTIVE）
· 唯一性状态不是生命周期状态：它是审核信息的一部分，不产生 question_event
· NOT_PROVABLE / UNIQUE_RISK 都不阻止 PENDING_REVIEW
  （所有新题本来就停在 PENDING_REVIEW）
· 现有 21 题中 ACTIVE 1 题的唯一性即使无法证明，也不影响其既有状态
  （P1-09-G 已量化：该题 standalone_risk=true，但在教材锚定标准下判 UNIQUE；
    本轮不修改它的任何状态）
```

## 8. 人工审核的重新定义

### 8.1 重新定义后的流程

```text
AI 生成 → 程序硬校验 → 独立 AI 英语质量审核 → 中文审核摘要
                                                     ↓
                          人工只需要确认：**这道题是否采用？**
```

### 8.2 中文摘要至少必须告诉用户什么

```text
1. AI 认为哪里有问题（具体到词句，例如"题干 Grandpa like 应为 Grandpa likes"）
2. 是否存在第二合理答案（选择题：列出未被排除的选项；
   填空题：明确说明"无法证明唯一"）
3. 是否有英语错误
4. 是否有学习价值
5. 是否与教材证据一致
6. 是否属于机械改写
7. 建议：保留 / 谨慎 / 不采用
```

并且**不得要求用户自己读英文做专业判断**（用户不是英语专业人员）：
摘要必须用中文写清"哪里有问题、为什么"。

（例如"write a picture 动宾搭配不当，应为 draw a picture"、
"和他的学生一起拉二胡…未被课文排除"）。

## 9. 生命周期最终机制（不变）

```text
GENERATED → VALIDATED → PENDING_REVIEW → APPROVED → ACTIVE
异常状态：REJECTED / DISABLED / STALE（与生命周期正交）
```

必须继续保持（全部已在 P1-08-C 实测）：

```text
AI 不能直接 ACTIVE（trg_ai_question_insert_active_forbidden）
AI 审核不能直接 APPROVED（转 ACTIVE 必须存在 actor_kind='human' 的 REVIEW_APPROVED 事件）
APPROVED 与 ACTIVE 必须是两个明确步骤（P1-08-C：批准后 active=0，未自动升级）
REJECTED 不能直接 ACTIVE（实测被拒）
STALE 不能绕过重新审核（实测被拒；重新审核路径需新的 REVIEW_APPROVED）
question_event 仍是生命周期事实源（append-only、不可 UPDATE / DELETE）
```

**一处设计上已知的缺口（本轮只指出，不实施）**：

```text
数据库层没有"ACTIVE 必须存在 evidence / validation / learning_object"的硬约束
（P1-08-C F2 已记录）。当前由唯一写入方 P1-07 的五表同事务保证。
是否补数据库层约束属于后续 schema 议题，不影响本轮收口。
```

**本轮不修改任何生命周期状态**：21 题仍为 ACTIVE 1 · PENDING_REVIEW 19 · REJECTED 1。

## 10. 成本与缓存机制

### 10.1 真实成本基准（全部实测，无编造）

| 环节 | 实测 | 来源 |
| --- | --- | --- |
| 生成（Section 级，1 次调用出多题） | **3,756.4 tokens/题**（4 次调用 / 22 题 / 82,641 tokens） | P1-06 |
| 整题式 AI 质量复核（10 题批次） | **914.6 tokens/题**（9,146 tokens） | P1-09-B |
| 整题式复核（15 题批次） | **1,024.7 tokens/题**（15,371 tokens） | P1-09-D |
| 逐候选复核（选择题，2 题） | **5,152 tokens/题**（10,304 tokens，reasoning 占 93.9%） | P1-09-F |
| 证据不足返回 0 题 | 4,154 prompt + 243 completion tokens，6.5 秒 | P0 第三场景 |

### 10.2 成本边界（按实测推导，不虚构价格）

```text
1. 生成阶段不凑题：0 题 Section 只需一次最短调用（P0 实测 6.5 秒 / 约 4.4k tokens），
   比"为了凑题再调一次"便宜，且不产生低质量题。
2. 质量审核只审核**已通过程序硬校验**的候选题 → 被硬校验拦掉的题永不进入 AI 审核
   （P1-07 实测：22 个候选中 19 个通过、3 个被拦）。
3. 0 题 Section 不需要 AI 审核（没有题可审）。
4. answer_unique 不做"昂贵的全量候选搜索"：
   · 选择题：候选 = 选项（3–4 个），一次调用内完成逐候选
   · 填空题：**不做**候选搜索（P1-09-E/G 判定不可行），只写 NOT_PROVABLE
   · 不做确定性风险预筛（P1-09-G BLOCKED：80% 误标 + 漏检，省不了钱）
5. AI 审核结果必须可缓存复用：
   · 以 `question_fingerprint`（64 hex 唯一索引）为缓存键，同一题不重复审核
   · 复核记录同时保存 `review_context_hash`：教材证据或提示词变化 → 缓存失效（对应 STALE 语义）
   · V1.3「AI 数据复用优先」Level 0–5 继续适用
6. 页面打开、列表展示、历史查看**不得**触发任何 AI 调用（V1.3 已冻结）。
```

### 10.3 一段必须写清的诚实结论

```text
逐候选协议在选择题上的成本是 5.15×/题（相对 P1-09-D 基线），而它的精度很低
（83% 的候选被判有效）。因此：
  · 它只能作为**可选的辅助信息**，不能作为每题的必经步骤；
  · 是否对某道选择题启用逐候选，应由人工需要决定（按需），而不是自动全量。

## 12. Blocker（不解决则收口无效；均不构成设计矛盾）

### B1 · 「正常 0 题」必须获得正式身份并被真实写入

```text
现状：guard 只区分 OK/TRUNCATED/EMPTY_CONTENT/API_ERROR；0 题与有题都返回 OK；
      generation_run 的 INSUFFICIENT_EVIDENCE 使用 0 次；7 行 q=0 全部为失败。
必须做：在生成流程中增加"0 题 + 理由"的判定，并写入
      generation_run.status = 'INSUFFICIENT_EVIDENCE' + insufficient_evidence = 1
      + note 记录具体理由（无需 schema 变更，字段已存在）。
不做会怎样：新原则"没有就 0 题"永远只是报告里的说法，
      下游仍会把 0 题当失败，并可能为了"避免失败"而补题。
```

### B2 · `answer_unique` 的最终表达必须有落脚点

```text
现状：数据库里没有任何字段能表达 NOT_PROVABLE / UNIQUE_RISK；
      question_validation 语义是程序验证结果，不得用于 AI/唯一性判断。
必须做（二选一，推荐先做前者）：
  ① 先落文件：structured/ai/quality_review/<run>.json（P1-09-C 已设计，零 schema 变更）
  ② 再落表：schema v3 纯新增 1 张 append-only 的 answer_uniqueness_assessment
     （P1-09-G 已给出最小字段，明确不建 signal / candidate 表）
不做会怎样：填空题的 NOT_PROVABLE 无处安放，中文摘要也无法引用该结论。
```

### B3 · 中文审核摘要必须有结构与最小内容

```text
现状：AI 能产出具体中文理由（P1-09-D/F 实测），但没有任何"给人看的中文摘要"结构，
      也没有"用户只回答采用/不采用"的载体。
必须做：定义摘要的最小内容（§8.2 的 7 条）与展示边界（§8.3），
      并与 B2 的落点一致（同一份 review 记录里出摘要字段）。
不做会怎样："人工只需确认采用/不采用"无法成立，用户仍要自己读英文判断，
      第 7 项检查会从 NON-BLOCKING 恶化为 FAIL。
```

### 12.1 为什么这些不是"设计矛盾"（因此本条不判 BLOCKED）

```text
三项的共性是"设计的必要落地件尚未接通"，而不是"设计本身自相矛盾"：
  · B1 的字段已存在（schema 无需变更）
  · B2 已有两种可行落点（P1-09-C 的文件方案 / P1-09-G 的单表方案）
  · B3 的内容已有实测依据（P1-09-D/F 的中文理由可直接作为模板）
且三项都能在"下一阶段最小实施范围"内完成。
```
