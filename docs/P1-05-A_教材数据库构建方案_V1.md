## 1. 目标与范围

目标：回答“按已冻结的 P1-04 模型，正式构建教材数据库时应如何安全实施”。

范围：

1. 确定内容包与学习者数据库的物理位置与分离方式。
2. 把 P1-04 逻辑实体映射为落地表结构，避免过度设计。
3. 定义 L1/L2/L3/L4 分层与写入权限边界。
4. 定义版本隔离、导入顺序、幂等、事务恢复与升级回滚机制。
5. 定义 Dry-run → Validate → Build → Acceptance 四步流程。

## 2. 核心原则（不可动摇）

1. **教材内容数据库是权威教材内容的结构化承载，不允许 AI 生成内容覆盖教材原始内容。**
2. **AudioMapping 在首次导入阶段全部保持 CANDIDATE，不得自动升级为 CONFIRMED_BY_HUMAN。**
3. **L3 AI 辅助层不能反向修改 L1 权威教材内容层。**
4. **L4 学习表现数据必须与教材内容数据库物理分离。**
5. 原始 PDF / 图片 / 音频只读，任何阶段不得修改、覆盖、重命名。
6. 当前统计数字（Unit 8 / Section 46 / Activity 96）是快照，不得写成程序校验常量以外的规则。

## 3. 内容包与学习者数据库的物理分离

```text
① 教材内容包（只读、版本化、可随 APP 发布）
   开发期：D:\ZhixueEnglish\structured\contentpack\v1\<textbook_id>.sqlite
   发布期：随 APP 打包进 assets，安装后解压到 app 私有目录

② 用户学习库（可写、私有、绝不随 APP 发布）
   Android：/data/data/<pkg>/databases/learner.db
   开发机：%LOCALAPPDATA%\ZhixueEnglish\learner.db

③ 构建与审计产物
   构建暂存：D:\ZhixueEnglish\structured\staging\
   构建报告：D:\ZhixueEnglish\audit\
```

分离理由：内容包可随教材重建与升级，用户数据不可重建必须独立备份；两者混放会导致“教材升级丢学习记录”。

## 4. SQLite 架构

- 采用 SQLite（Android 原生支持、单文件、事务可靠、支持 JSON1 / FTS5）。
- 内容包以**只读方式**打开；运行时模块对内容包只有 SELECT 权限。
- 用户库独立文件，独立事务，独立备份策略。
- 跨库关联只通过稳定业务 ID（`textbook_id` / `unit_id` / `activity_id` 等），**不依赖物理 rowid**。

## 5. L1 / L2 / L3 / L4 分层原则

```text
L1 权威教材内容层   ← 唯一事实源，仅来自教材 PDF / 官方音频
        ↓ 派生（只读引用）
L2 教材派生学习资源层  ← 词汇 / 短语 / 句型 / 语法 / 学习目标，必须挂 source_ref
        ↓ 引用
L3 AI 辅助层        ← 解释 / 提示 / 诊断 / 建议 / 生成练习，只能引用，不能反写
        ↓ 只读引用
L4 孩子学习表现层    ← 会话 / 作答 / 掌握度 / 巩固，只引用 ID，不复制教材正文
```

内容包中只包含 L1 与 L2；L3 允许保留空表；L4 在用户库中。


合并与 JSON 取舍：

- ImageAsset 与图片 block 合并为 `content_asset`。
- 稀疏字段用 JSON 列：`evidence.bbox_json`、`evidence.font_json`、`page.notes_json`、`parse_snapshot.stats_json`、`parse_snapshot.quality_json`。
- 需要索引 / 过滤 / 外键的字段一律独立列。

统一字段：`<entity>_id`、`textbook_id`、`snapshot_id`、`review_status`、`schema_version`、`created_at`。

## 7. textbook_id / snapshot_id 版本隔离

- `textbook_id` 由 publisher / 语言 / 年级册次 / 课标版本确定性生成，是根级版本标识。
- 所有子表均带 `textbook_id`，并建立复合外键，禁止跨教材引用。
- `snapshot_id` 标识一次解析快照：同一个 `textbook_id` 下可有多次快照，至多一个 `is_active`。
- 业务 ID（如 `<section_id>:A2`）与 snapshot 无关，**重建快照不改变业务 ID**，保证用户数据不失效。
- 内容包文件名携带 `textbook_id` 与 schema 版本。

## 8. ParseSnapshot

```text
parse_snapshot
├── snapshot_id
├── textbook_id
├── parser_name / parser_version / rule_set_version
├── input_pdf_sha256 / input_audio_count
├── build_started_at / build_finished_at
├── status            BUILDING / VALIDATED / FAILED / SUPERSEDED
├── stats_json        页数 / Unit / Section / Activity / 图片 / 音频
├── quality_json      控制字符 / 连字 / 页码映射 / 跨单元 / 编号异常 / 缺口
├── is_active
└── supersedes_snapshot_id
```

作用：回答“数据库中的内容来自哪一次解析”，支持 parser 改版后的追溯与整体回滚。

## 9. ImportBatch

```text
import_batch
├── batch_id
├── snapshot_id / textbook_id
├── started_at / finished_at
├── status            RUNNING / FAILED / SUCCESS / ROLLED_BACK
├── failed_stage / error_message
└── stage_records     → import_batch_stage（stage / row_count / last_key / status）
```

作用：任何阶段失败都能定位“导入到了哪里”，并支持断点续跑。

## 10. 导入顺序

```text
1  parse_snapshot
2  textbook_edition
3  source_artifact（PDF + 54 MP3）
4  page
5  unit
6  section
7  activity
8  content_block
9  content_asset
10 evidence
11 activity_content / sub_question
12 audio_asset
13 audio_mapping（全部 CANDIDATE）
14 source_ref
15 learning_item / learning_goal
16 质量校验（计数 + 抽样 + 快照比对）
17 切换 active snapshot
```

## 11. 幂等性

1. 稳定业务主键（确定性生成，不使用自增 rowid 作为业务标识）。
2. Upsert 写入：`INSERT … ON CONFLICT(business_key) DO UPDATE`。
3. 内容指纹：`content_hash`（`text_raw` + 关键字段）判断是否需要更新。
4. 快照隔离：新快照写入独立表空间，校验通过后原子切换 `is_active`。
5. 提供 `--dry-run` 与“同一输入必须得到相同统计结果”的回归校验。

## 12. 事务与失败恢复

- 以 snapshot 为回滚单元；每阶段一个事务 + 保存点。
- 绝不原地修改正在使用的快照；失败快照整体丢弃。
- 内容包升级失败不影响用户库；业务 ID 稳定，用户数据不受影响。
- 内容包可从 PDF + parser 重建；用户库必须独立备份。

## 13. 版本升级与回滚

- `schema_version`（结构版本）与 `rule_set_version`（解析规则版本）分离记录。
- 内容包按版本目录并列保存，切换只改“当前版本指针”。
- 回滚内容包 = 指回旧版本目录；回滚用户库 = 恢复备份文件。
- 用户库迁移“只增不删”，历史作答与掌握状态保留时间序。

## 14. NEED_REVIEW 保留原则

- 解析阶段未消除的不确定性必须原样进入数据库，不得因“看起来干净”而抹除。
- 当前已知待审项：Activity 边界 NEED_REVIEW 23 个、阅读顺序 NEED_REVIEW 88 页、Activity 编号缺口 17 处。
- 每条待审记录必须携带证据（bbox / 侧栏文本 / 页码），便于人工审核。

## 15. AudioAsset 与 AudioMapping 的关系

- `audio_asset`：54 个原始 MP3 的只读元数据（文件名不改、时长 / 码率 / 采样率 / 声道 / ID3）。
- `audio_mapping`：音频到教材节点的映射，**首次导入全部 `CANDIDATE`**。
- 允许候选映射存在多个目标或暂无目标；`CONFIRMED_BY_HUMAN` 只能由人工审核写入。

## 16. AI 不参与首次教材数据库构建

- 首次构建禁止：AI 生成解释、知识点、练习、Transcript、修改教材文本、自动确认音频、自动产生学习结论。
- L3 表可以存在但必须为空；AI 调用次数必须为 0。

## 17. Dry-run → Validate → Build → Acceptance 流程

```text
Dry-run   调用 parser + 读取 PDF/MP3 元数据，在内存中构建“即将导入的数据集合”，
          执行字段 / 主键 / 外键 / source_ref / 隔离 / 音频 / 重复 / hash / quality 检查，
          输出预计各表记录数与风险清单；不创建正式数据库。

Validate  人工核对 Dry-run 报告：冻结统计是否一致、是否存在 STOP 项、
          待审项是否与 P1-03-C 一致。

Build     在用户明确批准后，写入 contentpack v1 SQLite（只读内容包），
          生成新的 snapshot，校验通过后标记 is_active。

Acceptance 校验记录数、外键、source_ref、音频全部 CANDIDATE、AI 数据为 0，
           并保留构建报告与哈希，形成可回滚的正式版本。
```

## 18. 结论

本方案在不修改教材、不调用 AI、不确认音频映射的前提下，给出了内容包与用户库分离、分层清晰、版本可隔离、导入可回滚、失败可定位的实施路径，可作为 P1-05-B 正式构建的依据。
